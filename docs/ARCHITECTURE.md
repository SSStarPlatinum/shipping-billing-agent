# 架构与关键决策

## 1. 总体数据流

```
┌────────────────────────────────────────────────────────────────────────────┐
│ ① 摄入 Ingest                                                               │
│   EML → 邮件头/正文/HTML → 附件递归（PDF/图片/Excel/Word，最大 5 层）         │
│   PDF → 文本层优先；字符数不足视为扫描件 → OCR                                │
│   图片 → OCR；Excel → openpyxl/xlrd；Word → python-docx / LibreOffice        │
│   统一产物：RawDocument(text, pages, tables, metadata, attachments, warnings)│
└───────────────────────────────┬────────────────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ② 抽取 Extract（LangChain RunnableParallel）                                 │
│   规则通道：类型/编号/日期/双方/币种/合计/业务标识/明细行                      │
│   LLM 通道：语义补位（可选，Pydantic 结构化 + 缓存 + 解析修复重试）             │
│   融合：数值以规则为准，语义缺失用 LLM 补，冲突→降置信度                       │
└───────────────────────────────┬────────────────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ③ 标准化 Normalize   费用名词表 / ISO 4217 / PP-CC-COD                       │
└───────────────────────────────┬────────────────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ④ 决策 Decide（逐条费用，LangChain 链式节点）                                  │
│   校验 → 匹配（4 级）→ 角色/方向（AR/AP）→ 变更集（overwrite/enrich）→ 操作类型  │
│   置信度 < 阈值 / 有 error / 有冲突 / 主体不明 → PENDING_REVIEW               │
└───────────────────────────────┬────────────────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ⑤ 输出 Emit                                                                 │
│   results.json（标准结构 + 审计链） / ledger_after.json / report.md / run_log │
└────────────────────────────────────────────────────────────────────────────┘
```

## 2. 为什么是"三层模型"

| 层 | 类型 | 作用 | 为什么不能合并 |
|---|---|---|---|
| 证据层 | `RawDocument` | 原文、表格、页码、OCR 来源、附件树 | 出问题时要能回答"原文长什么样"，这是审计与复盘的根 |
| 语义层 | `ExtractedDocument` / `ChargeLine` | 结构化字段 + 逐字段置信度 + provenance | 抽取算法的中间态，便于规则/LLM 融合与再加工 |
| 输出层 | `OutputRecord` | 题目规定的 JSON 契约 | 对外契约必须稳定，不随内部模型演进变化 |

## 3. 关键决策与取舍

### 3.1 PDF：文本层优先，而不是"一律 OCR"

* 文本层是矢量原文，准确率 100%、零网络依赖、零成本；
* 扫描件（每页字符数 < 120）才转 OCR；
* 但保留 `--ocr-mode api` 强制全量 OCR，满足"必须调用 OCR API"的验收诉求；
* 代价：文本层的阅读顺序可能与视觉不一致（多栏票据会串行），所以字段抽取全部用"模式 + 上下文"而不是"坐标"。

### 3.2 费用行：布局模板 + 区块定位，而不是纯正则扫全文

* 纯"结尾是金额就当费用"会误抓箱号行、提单号行、地址电话；
* 先找表头（`DESCRIPTION…AMOUNT` / `CHARGES CUR AMOUNT` / `Base Rate…Amount` / 中文表头），
  再往下读到 `TOTAL/空行` 为止；
* 没有表头时，只接受"命中费用词表"或"高置信布局"的行；
* 8 种布局按信息量降序：多币种发票 → 单价/数量/P-C/金额 → 符号金额 → 币种+金额 → … → 仅金额。

### 3.3 表格：列语义映射，而不是固定列序

`extract/tables.py` 把表头词映射成 `charge/amount/currency/quantity/unit_rate/payment` 七种语义，
中英文同义词都覆盖（费用名称/金额/币种/数量/单价/付款方式…），因此 Excel、Word 表格、OCR 返回的 tables 共用同一套解析器。

### 3.4 规则 ∥ LLM 的并联，而不是串联

* 并联：两者看同一份原文，互不影响，任何一个失败都不阻塞主链路；
* 串联（规则失败才找 LLM）在工程上更省 token，但无法做**交叉校验**；
* 并联的代价是多一次模型调用，收益是"两个独立信源互相印证"——这正是低置信度判定的依据来源。

### 3.5 台账按记账主体隔离

`Ledger.scope_lines(entity)` 只返回"属于该主体"或"未标注主体"的行。
否则一个平台替多家公司管账时，A 公司的提单号可能匹配到 B 公司的账单——这是真实事故的高发点。

### 3.6 幂等与重复入账

* 批次内：`(单据号, 费用名, 金额, 币种)` 作为去重键，重复命中 → `PENDING_REVIEW` 而不是再 `CREATE` 一条；
* 台账侧：匹配成功且无 overwrite → `NO_CHANGE`，不会重复挂账；
* 缓存侧：OCR/LLM 结果按内容哈希缓存，重跑不会产生不同结果。

## 4. 扩展一个新格式需要改哪里

1. `ingest/xxx_loader.py` 实现 `parse_xxx() -> RawDocument`（文本 / 表格 / metadata）；
2. `ingest/dispatcher.py` 注册扩展名与魔数；
3. 若新格式有独特的费用表达，在 `extract/rows.py` 增加一个布局模板；
4. 补 2 个单测 + 1 个样例，跑 `pytest` 与 `eval`。

抽取、标准化、匹配、校验、输出层**完全不需要改**——这是分层的收益。

## 5. 目录与职责边界

| 目录 | 只允许做的事 |
|---|---|
| `ingest/` | 把字节变成 `RawDocument`，不做业务判断 |
| `extract/` | 把 `RawDocument` 变成 `ExtractedDocument`，不碰台账 |
| `normalize/` | 纯函数映射（名称/币种/付款方式），无 IO |
| `finance/` | 只做 AR/AP 判定，无 IO |
| `matching/` | 台账读写与匹配，不做校验 |
| `validation/` | 只产出 `Issue`，不决定操作类型 |
| `pipeline_utils.py` | 唯一决定 `operation` 的地方 |
| `harness/` | 横切能力：缓存/重试/日志/报告/评测 |

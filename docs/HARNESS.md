# Harness 工程化设计

> 对应验收标准第 8 条：**"当前场景下如何设计 harness 工程提升稳定性和输出准确性"**

"Harness" 在这里指**围绕模型/规则的外围工程骨架**：它不改变业务逻辑，但决定系统在真实环境里
是"偶尔能跑通"还是"每天能放心跑一万张单"。

---

## 1. 目标拆解

| 目标 | 具体表现 | 本文机制 |
|---|---|---|
| 稳定性 | 单文件失败不影响整批；外部依赖抖动可恢复 | 隔离、重试、超时、熔断 |
| 准确性 | 数字不能错；宁可转人工也不猜 | 双通道交叉校验、算术自洽、置信度阈值 |
| 可复现 | 同一输入永远同一输出 | 温度 0、内容哈希缓存、稳定排序 |
| 可观测 | 30 秒内回答"这条数字从哪来" | provenance、审计链、run_log、report |
| 可回归 | 改一行代码就知道有没有变差 | 金标准评测 + 89 个测试 |

## 2. 七层机制

### 2.1 输入隔离（Blast Radius）

```python
for path in files:
    try: raw = load_with_retry(path)
    except Exception: record_failure(); continue      # 单文件失败只记一条 failure
```

* 单文件解析失败 → 记录 `{file, stage, error}`，**整批继续**；
* 附件失败单独捕获，不拖垮邮件主流程；
* 附件递归深度上限 5 层，防止畸形 EML 造成无限递归。

### 2.2 重试 + 退避 + 超时

| 依赖 | 策略 |
|---|---|
| 文件解析 | 2 次重试（IO 抖动） |
| OCR API | 3 次重试，指数退避 `1.5^n`，连接 10s / 读取 300s 双超时 |
| LLM | 2 次重试，含"解析失败 → 重新请求"的修复循环 |

`harness/resilience.py::retry` 实现了带抖动的指数退避，避免重试风暴同时打到网关。

### 2.3 熔断（Circuit Breaker）

OCR 连续失败 3 次 → 打开熔断 60s，本批后续文件直接走缓存/文本层。
**收益**：一个坏依赖不会把 10000 张单的处理时间拖成 10000 × 300s。

### 2.4 内容哈希缓存（Idempotency）

```
data/ocr_cache/<sha256(file)>.json
data/llm_cache/<sha256(model+prompt)>.json
```

* 同一份文件重跑 → 命中缓存，结果逐字节一致；
* 缓存可回放 → 评审/CI 无网络也能跑；线上问题可"复现-修复-重放"；
* 缓存带 `_meta`（来源、时间、endpoint、fixture 标记），不会把"回放"伪装成"实时识别"。

### 2.5 双通道交叉校验（Accuracy Gate）

```
规则通道 ──┐
           ├─→ 金额一致？编号一致？合计一致？  → 一致：加分；不一致：降置信度 + 告警
LLM 通道 ──┘
```

真实场景里，两个独立信源同时错的可能性远低于单通道。冲突时不选边，而是**降低置信度交给人**。

### 2.6 确定性（Reproducibility）

* LLM `temperature=0`；
* 文件按名称排序后处理；台账行匹配时按 `(金额距离, bill_id)` 稳定排序；
* 不依赖当前时间做业务判断（时间只进日志）；
* 同一输入在 `--no-llm` 下输出**完全确定**，这是做回归测试的前提。

### 2.7 可观测（Observability）

每条记录都带：

```json
"source": {"file": "...", "locator": "line 26", "ocr_source": "pdf_text_layer",
           "extractor": "rules", "document_sha256": "70dcc3e..."},
"confidence": 0.82,
"matched_bill_id": "BILL-1001",
"match_rule": "单据编号+费用名称",
"field_changes": [{"field": "amount", "old": 40.0, "new": 65.0, "kind": "overwrite"}],
"warnings": ["交易双方信息不完整"]
```

再加 `run_log.json`（逐文件耗时/状态/错误）与 `report.md`（人读版），
线上排障不需要翻日志猜。

## 3. 准确性的四道闸门

| 闸门 | 规则 | 结果 |
|---|---|---|
| ① 结构闸 | 金额必须是数字；币种必须 ISO 4217 | 不满足 → `error` → PENDING_REVIEW |
| ② 算术闸 | `单价 × 数量 = 金额`；`Σ明细 = 单据合计`（容差 0.02 / 0.5%） | 不满足 → warning + 扣分 |
| ③ 语义闸 | 记账主体必须是单据一方；单据类型只能修正方向不能决定方向 | 不满足 → PENDING_REVIEW |
| ④ 统计闸 | 综合置信度 ≥ 0.55（可配） | 不满足 → PENDING_REVIEW |

四道闸门全部通过才允许 `CREATE/UPDATE/NO_CHANGE`。样例中 3/7 条记录停在人工复核，
正是闸门在起作用，而不是系统"抽不出来"。

## 4. 评测（Regression Gate）

`python -m shipping_billing eval`：

```
recall / precision / operation_accuracy / posting_accuracy / 字段级准确率
+ mismatches（哪条对不上，期望 vs 实际）
```

* 金标准 `data/expectations/golden.json` 是**人写的**（不是从输出反抄的），所以能真正发现回归；
* CI 里 `pytest -q && python -m shipping_billing eval` 一起跑，任一失败即阻断；
* 指标口径（按 `文件+费用名+金额` 对齐）写死在 `harness/evaluation.py`，避免"换个口径就 100%"。

## 5. 错误分类学（决定"要不要重试"）

| 类别 | 例子 | 处理 |
|---|---|---|
| 瞬时故障 | 网络超时、5xx | 重试 + 退避 |
| 依赖故障 | 网关 504 持续 | 熔断 + 回落缓存 |
| 数据问题 | 文件损坏、缺页、编码乱 | 不重试，记录后跳过 |
| 业务问题 | 金额与合计不符、找不到主体 | 不重试，降级 + 转人工 |
| 程序缺陷 | 未捕获异常 | 记录堆栈，整批继续 |

把"重试"和"降级"分开，是避免"用重试掩盖数据问题"的关键。

---

## 6. 生产化还需要补的三件事

1. **并发与限流**：按 OCR/LLM 的 QPS 配额做令牌桶，把"重试"限制在配额内；
2. **存储升级**：台账从 JSON 迁到数据库，需要行级锁 + 版本号（当前是单进程文件写回）；
3. **人在环**：`PENDING_REVIEW` 的结果要落成待办队列（含原文截图/高亮），人工修正后回流成新的金标准样本，
   形成"越用越准"的闭环。
